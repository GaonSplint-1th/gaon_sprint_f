# 화면 ↔ 디자인 대조 기록

작성일: 2026-08-24 · 대상 브랜치: `feature/api-integration` (PR #13)

퍼블리싱된 Figma 화면과 실제 구현을 대조한 결과다.
**Figma 프레임 이름이 내용과 어긋나는 경우가 많아** 이름만 보고 화면을 판단하면 안 된다.
아래는 실제로 열어서 내용을 확인한 기록이다.

---

## 1. 라우트 ↔ 디자인 대응표

| 라우트 | 화면 | 대응 Figma 프레임 | 상태 |
| --- | --- | --- | --- |
| `/ingredient-register` | 보유 식재료 등록 (**진입점**) | `01보유식재료등록`, `02식재료등록완료`, `03식재료검색`, `031식재료검색결과x`, `안내` | 구현 완료 |
| `/edit` | 식단 수정 | `08메뉴수정하기`, `09메뉴수정하기` + 상세 동작 이미지 | 재구현 (3-3) |
| `/recommend` | 식단 추천 | `04식단 추천skeleton`, `05식단 추천`, `06식단추천 선택됨`, `07식단 미리보기` | 구현 완료 |
| `/` | 오늘의 식단 (홈) | `10메인 홈 화면(이번주 식단, 재료)` | 구현 완료 |
| `/recipe/:id` | 레시피 | `11주간식단(…)`, `12주간식단(…)`, `주간식단(…)` ×2 | 구현 완료 |
| — | 에러 팝업 3종 | `네트워크 오류`, `서버 점검 및 오류`, `업데이트 안내 모달` | `ErrorPopup` 공용 컴포넌트로 구현 |
| `*` | 404 | 없음 | 디자인 없음, 라우터상 필요해 유지 |

**사용자 흐름**: 식재료 등록(진입) → 식단 추천 → 식단 수정 → 오늘의 식단(홈)

`/` 로 들어와도 현재 식단이 없으면(백엔드 404) 식재료 등록으로 보낸다.
식재료를 등록해 식단을 만들어 오는 것이 정해진 진입 흐름이고,
홈은 흐름의 **끝**이지 시작이 아니다. 그래서 시안 10에 하단 CTA가 없다.
식단이 있는 유저는 `/` 에서 그대로 홈을 본다.

---

## 2. 디자인 쪽 문제 — 프레임 이름이 내용과 다름

### 2-1. "주간식단"이라는 화면은 존재하지 않는다

프레임 4개가 `주간식단(메인홈보다는상세)` 계열 이름을 달고 있으나,
**내용은 전부 레시피 화면**이다.

| 프레임 이름 | 실제 내용 |
| --- | --- |
| `11주간식단(메인홈보다는상세)` | 메뉴 이미지 영역 · 계란토스트 · 재료보기 · 조리순서 · 레시피 |
| `12주간식단(메인홈보다는상세)` | 위와 같음 + 조리 단계 본문 |
| `주간식단(메인홈보다는상세)` ×2 | 위와 같음 + 재료보기 코치마크 |

→ 이름만 보고 "주간 식단 상세 화면을 새로 만들어야 한다"고 판단하기 쉽다. **만들 화면이 아니다.**
→ 제안: `11레시피`, `12레시피 상세`처럼 내용에 맞게 이름 변경.

### 2-2. 홈 프레임 이름에 없는 기능이 적혀 있다

`10메인 홈 화면(이번주 식단, 재료)`

- 이름에는 **"이번주 식단"**과 **"재료"**가 있으나, 화면 내용은 `오늘의 식단` 하나뿐이다.
- 주간 단위 보기도, 재료 섹션도 프레임 안에 없다.

→ 기획이 빠진 것인지, 이름이 낡은 것인지 확인 필요.

### 2-3. 중복 프레임이 많다

퍼블리싱 세트 **17프레임 = 실제 7화면**이다. 중복 현황:

- 식단추천 선택됨: `06`, `07`, `식단추천 선택됨` (3개)
- 메뉴수정하기: `08`, `09`, `메뉴수정하기` (3개)
- 레시피: 4개 (위 2-1)

→ `08`/`09`는 `확정하기(0/7)` vs `(7/7)` 상태 차이라 의미가 있지만,
번호 없는 `메뉴수정하기`·`식단추천 선택됨`은 구버전으로 보인다.

### 2-4. `07식단 미리보기`에 미리보기 모달이 없다

이름은 "식단 미리보기"인데 퍼블리싱된 내용은 `06식단추천 선택됨`과 동일하다.
모달 레이어가 퍼블리싱에서 빠진 것으로 보인다.

→ 참고로 초기 SVG(`07식단 미리보기.svg`)에는 모달이 있었다. 그쪽이 정본이다.
→ 현재 구현은 SVG 기준으로 만들어 두었다.

### 2-5. 식사 카드 왼쪽 열 너비가 실데이터에 안 맞는다

`08/09메뉴수정하기`의 카드 왼쪽 텍스트 열이 `w-61px`로 고정돼 있다.

- Figma가 placeholder(`메뉴명`, `약 000원`) 기준으로 잡은 hug 너비로 보인다.
- 실제 메뉴명(`돼지고기 김치찌개`)이 들어가면 심하게 줄바꿈된다.

→ 구현에서는 남는 공간을 쓰도록(`flex: 1`) 했다. 의도적 고정이면 알려줄 것.

## 3. 구현 쪽에서 정리한 것

### 3-1. 지운 것

| 대상 | 이유 |
| --- | --- |
| 홈 하단 `식단 추천` 버튼 | 시안 10 하단에 요소가 없음. 대신 식단이 없을 때만 진입점(식재료 등록)으로 보내 경로가 끊기지 않게 함 |
| `/recommend/loading` 라우트 | `/recommend`와 같은 컴포넌트를 가리키던 중복. `04` 스켈레톤은 목록 조회 중 상태로 처리 |
| `/error-check` 페이지 | 에러 팝업을 눌러보는 개발용 화면. 디자인에 없음 |

식사 슬롯 수정 API(`useUpdateDish`/`useDeleteDish`/`useRerollDish`)와
요리 목록(`useDishes`)은 서비스 레이어에 그대로 남아 있다. 화면만 제거했다.

### 3-2. 추가한 것

| 대상 | 근거 |
| --- | --- |
| 온보딩 안내 3종 (식재료 등록·식단 추천·레시피) | 시안 `안내`, 와이어프레임 p01/p02/p30 |
| `한글로만 검색할 수 있어요.` | 시안 `01` |

### 3-3. `/edit` 재구현 경위 (2026-08-24)

`확정하기(0/7 → 1/7)`의 의미를 잘못 구현한 화면이었다.

- **잘못된 이해**: 끼니 메뉴를 바꾸는 화면이고, 카운터는 "메뉴가 채워진 요일 수"
- **실제 기획**: 메뉴를 수정하는 화면이 아니다. `확정하기`는 **하루를 확정할 때마다**
  숫자가 올라가는 진행도다 (0/7 → 1/7 → … → 7/7)

이 화면은 내 작업 이전부터 있었다(`a957bc7 refactor: split home diet pages`).
당시에도 하드코딩 `options` 배열로 메뉴를 바꾸고 `changedCount`(바꾼 메뉴 수)를
세고 있었다. 나는 그 구조를 그대로 두고 API 만 연결했고, 잘못된 전제를 걷어내지
못했다. 시안(08/09)에 맞춰 다듬는 작업까지 한 뒤에야 기획 오류가 드러났다.

**바로잡은 뒤 다시 만들었다.** 이 화면이 하는 일은 메뉴 교체가 아니라:

1. 날짜를 넘기며 그날의 세 끼를 확인한다 (세로 스크롤)
2. 카드를 옆으로 밀면 삭제 버튼이 나오고, 누르면 그 끼니를 비운다
3. `확정하기` 로 하루를 확정하면 `0/7 → 1/7` 로 오르고 다음 날로 넘어간다

`확정` 상태는 백엔드에 저장할 API 가 없어 `localStorage`
(`gaon.confirmedDays.<weeklyMenuId>`) 에만 둔다. 식단이 바뀌면 0 부터 다시 센다.
API 가 생기면 `pages/MenuEdit/useConfirmedDays.ts` 를 그쪽으로 옮기면 된다(4-5).

## 4. 남은 확인 사항

1. **주간 식단 화면이 정말 필요한가** (2-2). 홈 프레임 이름에만 존재한다.
2. **재료 섹션**이 홈에 들어가야 하는가 (2-2).
3. **식단 추천 카드 문구**: 시안은 메뉴 이름 3개(`제육볶음 · 김치찌개 · 계란찜`)였으나,
   백엔드가 카드용 요약 문구(`highlight`)를 자동 생성하게 되어 그쪽을 쓰고 있다.
   메뉴 이름으로 되돌리려면 카드마다 상세 조회가 다시 필요하다(요청 1회 → 1+N회).
4. **구버전 프레임 정리** (2-3).

### 온보딩 안내 적용 현황

| 화면 | 와이어프레임 | 상태 |
| --- | --- | --- |
| 보유 식재료 등록 | p01 / p41 | 적용 |
| 식단 추천 | p02 / p42 | 적용 |
| 레시피 | p30 / p44 | 적용 |
| 식단 수정 | p03 / p43 | 화면 자체가 삭제돼 해당 없음 (3-3) |
| 오늘의 식단(홈) | 없음 | 시안에 안내가 없다 |

각 화면에 처음 들어오면 한 번 자동으로 뜨고, 이후에는 앱바 ⓘ 로만 다시 연다.
본 기록은 `localStorage` 의 `gaon.guideSeen.<화면키>` 에 남는다.
5. **"하루 확정" 기능의 화면과 API**. `확정하기(n/7)`을 구현하려면
   요일별 확정 상태를 저장할 곳이 필요한데, 현재 API 명세에 해당 엔드포인트가 없다.
   화면 퍼블리싱과 백엔드 설계가 함께 필요하다.
